# 3. Ed25519 JWT Authentication

> **Date:** 2026-05-30
> **Status:** Accepted

## Context

The API needs stateless authentication for both user sessions and service-to-service calls. Symmetric HMAC (HS256) would require every service to share a secret, increasing blast radius if compromised. RSA is established but produces large signatures. We need a modern, compact, high-security alternative.

## Decision

- **Ed25519** asymmetric key pair for JWT signing (EdDSA algorithm, `EdDSA` in JOSE header)
- JWKS endpoint at `/.well-known/jwks.json` for key distribution
- Two key slots: `PRIMARY` (signs new tokens) and `SECONDARY` (verifies old tokens during rotation)
- Access token TTL: 15 minutes; refresh token: rotating opaque tokens (32 random bytes, base64, hash stored in DB)
- Service-to-service tokens include `aud` claim scoped to target service

## Consequences

### Positive
- 64-byte signatures vs 256+ bytes for RSA 2048 — smaller tokens, faster verification
- No shared secret — each verifier needs only the public key from JWKS
- Key rotation is seamless: publish new key as PRIMARY, demote old to SECONDARY, drain in-flight tokens, remove

### Negative
- Ed25519 has less universal library support than RS256 (but is well-supported in Node crypto, jose, and jwk-to-pem)
- Two-key-slot model adds complexity to key management code

### Neutral
- HMAC HS256 remains available for local development convenience (`NODE_ENV=development` only)

## Alternatives Considered

| Option | Pros | Cons | Why rejected |
|--------|------|------|-------------|
| HS256 (HMAC) | Simple, fast | Shared secret across all services; no key distribution | Unacceptable blast radius |
| RS256 (RSA) | Universal library support | Large keys, slow sign/verify, 2048+ bit minimum | Ed25519 is better on every axis |
| ES256 (ECDSA P-256) | Compact, fast | NIST curve concerns; Ed25519 is simpler and safer | Ed25519 chosen for simplicity |
